Publish an experience to Hydra

If you build in Unreal Engine, your project can run as a streamable experience on Hydra — packaged, delivered, and driven through a single lifecycle: draft to staging to live.

You register it once in HydraExperienceLibrary, then move it forward one command at a time. There are two ways to get a build in: deliver it by hand, or let Perforce stage it for you automatically. Both feed the same lifecycle.

Perforce → package → deliver → register → stage → promote → stream

One experience, one lifecycle. The steps below cover manual delivery (mode A); the automated Perforce path (mode B) collapses deliver + stage — you still package the build, then submit it.

{{/* ===== MODE A: manual delivery, numbered ===== */}}

Mode A · Manual
Deliver a build by hand

Package on Windows, upload to the release server, then walk the experience through its lifecycle. Best for a first build or an occasional update.

Package the UE project with HydraUnrealEngine

Copy the packager to Windows and run it from WSL via PowerShell. Preflight checks (Live Coding, GameplayStateTree, etc.) run by default; pass --skip-preflight to bypass them for a Blueprint-only project.

# Copy the HydraUnrealEngine binary to Windows
cp bin/hydraunrealengine.exe /mnt/c/Builds/

# Package (from WSL, via PowerShell)
powershell.exe -Command "C:\Builds\hydraunrealengine.exe package \
  'C:\Path\To\YourProject.uproject' \
  --engine 'C:\Program Files\Epic Games\UE_5.7' \
  --platform Win64 \
  --config Shipping \
  --output 'C:\Builds\your-project-packaged'"

Flags that matter:

  • --engine — explicit engine path (required if the .uproject has no EngineAssociation)
  • --no-compile — skip C++ compilation (Blueprint-only projects)
  • --skip-preflight — skip preflight checks (Live Coding, GameplayStateTree, etc.)
  • --config — build config: Development, Shipping (default), etc.

Deliver the packaged build to the release server

Create the versioned target directory and rsync the packaged output up. The layout under builds/ is <name>/<version>/; increment the version for each new build.

# Create the target directory
ssh root@releases.experiencenet.com \
  "mkdir -p /var/www/releases/builds/your-project/1"

# Upload
rsync -avz --progress \
  "/mnt/c/Builds/your-project-packaged/" \
  root@releases.experiencenet.com:/var/www/releases/builds/your-project/1/

This rsync-to-releases.experiencenet.com path is the canonical delivery method for manual (mode A) builds — see the note at the bottom of the page.

Register the experience in HydraExperienceLibrary

Create the experience record. It starts in draft.

ssh root@<experiencelibrary-host> "hydraexperiencelibrary create your-project \
  --label 'Your Project' \
  --owner <owner> \
  --developer <developer> \
  --release-path builds/your-project \
  --district <district> \
  --venue <venue> \
  --auto-promote=false"

Stage it

Point the experience at a build version. This transitions it from draft to staging.

ssh root@<experiencelibrary-host> "hydraexperiencelibrary stage your-project --cl 1"

Promote to production

Once it checks out in staging, promote. This copies the staging CL to production and sets the status to live.

ssh root@<experiencelibrary-host> "hydraexperiencelibrary promote your-project"

Verify

Confirm the record, the build files, and the fleet-wide overview.

# Check experience details
ssh root@<experiencelibrary-host> "hydraexperiencelibrary get your-project"

# Check build files
ssh root@releases.experiencenet.com "ls /var/www/releases/builds/your-project/1/"

# Overview of all experiences
ssh root@<experiencelibrary-host> "hydraexperiencelibrary status"

You can also review experiences in the web admin at https://hydraexperiencelibrary.experiencenet.com/admin.

{{/* ===== MODE B: automated Perforce ===== */}}

Mode B · Automated (Perforce)
Let Perforce stage it for you

For projects that submit to a stream depot, staging is hands-off. This is the live path behind Gallo-Romeins / Cyborn. Preferred for frequent delivery.

Submit the packaged build via Perforce

You still package the build yourself (mode A, step 1). Instead of rsyncing it, submit the packaged output to the project's stream depot under Builds/ — for Gallo-Romeins that is //galloromeinsmuseum/main/Builds/.

The watcher detects the new changelist

The HydraPerforce watcher (hydraperforcewatcher), running beside the Perforce server, sees the submit and publishes the packaged build to the fleet.

A build notification webhook fires

POST /api/v1/builds/notify is sent to ExperienceLibrary.

ExperienceLibrary updates the staging CL

It transitions the experience from draft to staging automatically — no manual stage --cl needed.

Promote when ready

The one manual gate that remains:

ssh root@<experiencelibrary-host> "hydraexperiencelibrary promote galloromeins"

The linkage. Set the experience's --watch flag to match the HydraPerforce watch-target name, so submits to that depot auto-stage. Gallo-Romeins uses watch target galloromeins against depot //galloromeinsmuseum/main.

# On create, or update later — bind the experience to a Perforce watch target
hydraexperiencelibrary create galloromeins \
  --label 'Gallo-Romeins' \
  --release-path builds/galloromeins \
  --watch galloromeins

With --watch set, mode B replaces steps 2 and 4 of mode A (deliver and stage): you still package the build (step 1), then each submit is delivered and staged on its own, leaving you only promote.

{{/* ===== Command table ===== */}}

Command reference

The HydraExperienceLibrary verbs that move an experience through its lifecycle.

CommandDescription
createCreate a new experience (starts as draft)
stage --cl <n>Set staging build, transition draft to staging
promotePromote staging build to production (live)
rollbackRevert production to previous build
pausePause a live or staging experience
resumeResume a paused experience
retireRetire an experience (any status)
Your experience is live. Registered once, it moves through draft → staging → live one command at a time, and rolls back the same way. Deliver by hand when you need to; wire up --watch and every Perforce submit stages itself — leaving promote as the only button you press.

Which delivery method is canonical

The two modes are not equivalent — pick deliberately. And a few rules will save you an afternoon on the Unreal side.

Manual delivery is canonical rsync-to-releases.

For a manual (mode A) build, the source of truth is rsync of the packaged output to releases.experiencenet.com:/var/www/releases/builds/<name>/<version>/, followed by create / stage. Do not invent other upload channels — the release server path is what --release-path resolves against.

Perforce auto-publish (mode B) is preferred for frequent delivery.

If the project ships often, wire --watch to the HydraPerforce target instead of rsyncing by hand. Manual delivery stays the fallback and the first-build path; automated staging is the steady-state path. Gallo-Romeins runs on mode B.

Set --watch to the exact HydraPerforce target name, or auto-staging silently won't fire.

In the automated Perforce path the build-notify webhook only auto-stages the experience whose --watch value matches the watch target (e.g. galloromeins); a mismatch leaves the experience stuck in draft.

Preflight can give a false all-clear on plugin-source projects.

A UE project with no top-level Source/ directory (its C++ lives under Plugins/) can pass preflight clean and then fail to compile downstream. Do not trust a green preflight for plugin-source projects — verify the build actually compiles before delivering.

GameplayStateTree forces compilation.

UE 5.7 templates may ship with the GameplayStateTree plugin enabled, which forces code compilation even on Blueprint-only projects. If you hit an error about a missing Binaries\Win64\*Editor.target, package with --no-compile or disable it in the .uproject:

{ "Name": "GameplayStateTree", "Enabled": false }
Stream depots need a stream-bound client to submit.

These are Perforce stream depots (e.g. //galloromeinsmuseum/main), so p4 submit requires a stream-bound client (Stream: //depot/main); a classic View-mapping client fails with "cannot submit from non-stream client."

Keep Binaries/, Build/ and Intermediate/ out of source control — but NOT Binaries/ThirdParty/.

Those compiled dirs are rebuildable junk and should never be submitted, but Binaries/ThirdParty/ holds NVIDIA/DLSS redistributables (e.g. under Plugins/Runtime/Nvidia/**/Binaries/ThirdParty/) that cannot be rebuilt from source. A broad cleanup sweep can delete these DLLs — exclude ThirdParty explicitly.

CRLF line endings will break the downstream compile even when your source looks fine.

A Perforce import that stores literal CRLF inside text+x files produces \r\r\n on Windows sync and triggers MSVC C4335 "Mac file format detected" across compiled-source files. Normalize source to canonical LF before delivery.

Version directories are <name>/<version>/; increment every build.

Never overwrite an existing version directory on the release server — bump the number and stage --cl <n> at the new version.
